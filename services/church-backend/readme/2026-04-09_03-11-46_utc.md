## Visao geral

Este projeto e um backend Django 6 voltado ao fluxo de visitantes da IEADPG. O sistema concentra:

- autenticacao por telefone + OTP
- administracao interna via Django Admin/Unfold
- API publica do fluxo de visitantes via Django Ninja
- notificacoes com entrega imediata ou agendada
- integracoes externas com WhatsApp, voz e IA
- processamento assincrono via Taskiq + Redis

Rotas publicas principais:

- `/` redireciona para `https://ieadpg.org`
- `/admin/` abre o painel administrativo
- `/visitors/*` expoe a API de onboarding de visitantes

## Stack principal

- Python 3.12
- Django 6
- Django Ninja
- Ninja JWT
- Taskiq

- Unfold para admin

Integracoes de servico:

## API de visitantes

O fluxo publico atual esta concentrado em `apps/visitors/api.py`.

Rotas:

- `POST /visitors/authentication`
- `POST /visitors/login`
- `POST /visitors/refresh`
- `GET /visitors/data`
- `POST /visitors/data`
- `GET /visitors/address`
- `POST /visitors/address`
- `GET /visitors/religious-data`
- `POST /visitors/religious-data`

Fluxo:

1. `authentication`
   - cria ou reaproveita um visitante
   - dispara envio de OTP
   - aceita fluxo online ou presencial por `is_in_person`
2. `login`
   - valida `profile_uuid + otp`
   - retorna `access`, `refresh`, `is_visitor` e `status`
3. `refresh`
   - renova o par JWT
4. `data`
   - le e grava dados principais
5. `address`
   - le e grava endereco
6. `religious-data`
   - le e grava dados religiosos

### Status do visitante

Fluxo online:

- `1` `NEW_ONLINE`
- `2` `DATA_COMPLETED_ONLINE`
- `3` `ADDRESS_COMPLETED_ONLINE`
- `4` `AWAITTING_PRESENTIAL_VISIT`

Fluxo presencial:

- `11` `NEW_PRESENCIAL`
- `12` `DATA_COMPLETED_PRESENCIAL`
- `13` `ADDRESS_COMPLETED_PRESENCIAL`
- `14` `AWAITING_TO_COLLECT_YOUR_GIFT`

Status reservado para expansao:

- `21` `AWAITING_RECEPTION_CONTACT`

Observacao: o status `21` existe no dominio e nas notificacoes, mas foi mantido sem alteracoes de fluxo nesta rodada porque ele serve a uma etapa futura do produto.

## Notificacoes e tasks

### Pipeline atual

1. Um dominio cria uma `Notification`
2. `notifications/signals.py` reage no `post_save`
3. O enqueue acontece em `transaction.on_commit`
4. `notifications/services/queue.py` decide a estrategia:
   - `taskiq`
   - `eager`
   - `eager_fallback`
   - `disabled`
5. `notifications/tasks.py` processa a entrega assincrona

### Taskiq

Arquivos operacionais:

- `core/broker.py`
- `core/taskiq.py`
- `run_dashboard.py`
- `run_scheduler.py`
- `start_worker.sh`

Tasks principais:

- `process_notification_async(notification_id)`
- `check_and_process_scheduled_notifications()`

Observacao importante:

- a task de teste que enviava mensagem automaticamente a cada minuto foi removida
- ficou apenas a task real de processamento de notificacoes agendadas
